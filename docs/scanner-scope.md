# Single fixed scanner origin (US-005.2 application phase)

The deployment accepts one operator-configured HTTP/HTTPS origin. Reusable worker
code rechecks a saved job's target and generates its exact ZAP context rule before
claiming it. This is the approved smaller application phase of US-005.2, not
completed crawl/network enforcement. The deployed worker remains idle.

US-007.2 adds a reusable [baseline adapter](zap-baseline.md) that applies this
context to the packaged spider and collects passive/active execution evidence.
The deployed worker is still idle; complete redirect and network-enforcement
acceptance must not be inferred from the earlier scope-matching tests.

## Configuration

```dotenv
TARGET_ALLOWED_ORIGINS=["https://scan.example.com"]
```

An origin means scheme, hostname and port. HTTPS's default port is 443; HTTP's is
80. All paths within that origin are allowed, including `/page`, `/api` and `/docs`.
There is no path-prefix setting. Subdomains, another scheme, a different port and
other domains are rejected. An explicit default port, case-insensitive hostname
and optional terminal DNS dot are equivalent. Public IP literals remain supported.

`[]` denies every submission and worker handoff. More than one array entry is a
configuration error, including duplicates. Existing deployment configurations
containing multiple entries must be reduced before application startup. Changing
the environment requires recreating the affected Compose service, not merely
restarting its process with the old container environment. The private `.env` is
not edited by this phase. The operator must configure an origin they are authorized
to scan. The configured origin is global, not a per-team domain registry.

## Components and flow

1. `get_target_policy` in `app/core/target_policy.py` reads zero or one origin.
   Production submission reuses the existing identity/team and public-address
   checks. The underlying injectable `TargetPolicy` class still supports multiple
   origins for existing internal tests; deployment loading and scanner scope
   construction enforce the single-origin rule.
2. `app/workers/zap.py:handle_message` validates the shared message against the
   immutable stored job, then uses the current environment policy or an explicitly
   injected test policy. Unknown/mismatched jobs perform no target lookup.
3. `fixed_origin_scope` in `app/scanners/scope.py` rechecks exact origin and current
   public IPv4/IPv6 resolution. Any restricted/mixed/empty response denies it.
   A 403 policy denial becomes `target_denied` without claiming or mutating the
   job. Empty configuration also returns that decision. Operator configuration
   errors and unexpected exceptions propagate; they are not scan outcomes.
4. After a successful leased claim commits, the adapter receives the immutable
   `ScanRequest(job_id, url, claim_token, scope_regex)`. The rule is generated by
   trusted application code, not supplied in an API request or queue message.
5. `configure_scope(zap, request)` creates a context unique to the job/attempt,
   includes the exact origin and marks it in scope. It returns the context name
   or raises on configuration failure. It neither opens a URL nor starts a scan.
   The future adapter must configure a fresh ZAP instance before target requests
   and supply this context name when starting its spider. Reusing an instance
   with unrelated existing contexts is outside this callable contract.

The regex accepts only the origin and its paths, supports default-port equivalence
and escapes special characters. Python tests inspect matching behavior; US-007.2
additionally verifies the context in real ZAP against an isolated link fixture.
Comprehensive redirect behavior remains unverified. DNS resolution occurs before the leased
claim; no lease is spent resolving the target. Callers should keep transactions
short and handle denial/recovery through the future message-consumer policy.

## Patterns and limits

This reuses [Adapter](design-pattern/adapter.md): scanner-specific context setup
stays separate from job persistence. [Dependency Injection](design-pattern/dependency-injection.md)
supplies controlled policies/resolvers and scanner clients to tests. The existing
immutable request carries scope metadata. No new pattern, proxy, gateway container,
socket relay, Docker configuration, database migration or dependency is introduced.

The preclaim check is a point-in-time DNS check. It does not pin connections or
prevent the approved hostname resolving differently later. A matching URL rule
also does not prove that ZAP will never follow an out-of-scope redirect. US-007.2
checks discovered-link exclusion; comprehensive redirect verification and enforceable outbound
network restrictions remain AWS deployment work. A broad HTTPS outbound rule alone
would not implement origin isolation. No claim of full SSRF protection is made.

The original US-005.2 description and NFR-007/AC-010/AC-018 include enforceable
egress and actual crawl behavior. They are not rewritten or marked satisfied by
this phase. US-005.2 stays open. Existing API authentication/authorization remains
active. No test launches a real scanner or contacts a target.

## Verification

`tests/unit/test_scanner_scope.py` checks origin/path matching, redirect and link
candidate rejection, current private/mixed resolution denial, missing/multiple
configuration, IPv4/IPv6 literals, context configuration and safe setup failures.
Context calls use recording clients; candidate matching is not a real redirect
test. `tests/unit/test_target_policy.py` adds multi-entry configuration rejection.

`tests/integration/test_zap_worker.py` uses disposable migrated PostgreSQL schemas
with controlled DNS. It verifies target changes, private resolution and empty
configuration preserve the pending job and never invoke the adapter, alongside
the existing committed-claim and concurrency tests. No permanent jobs are created.
See the [test guide](../tests/README.md#us-0052-single-origin-application-phase)
for commands and actual check outcomes.
